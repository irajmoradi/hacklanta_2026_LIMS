## Routes

All routes below require authenticated village membership (403 for nonmembers).
Existing demo authentication works. Prefix: `/api/villages/{vid}`.

| Method | Route | Response |
| --- | --- | --- |
| GET | `/mayor/memory` | `{village_id,document:{weeks,facts,recent},updated_at,max_bytes,source}` |
| GET | `/mayor/event-templates` | `{version:1,templates,recovery}` |
| GET | `/mayor/effects` | `{weather,crater,house_downgrade,pet_sad,repairs:[{event_id,repair_event_id,penalty}]}` |
| GET | `/gazette/latest` | Latest edition; 404 before the first publication |
| GET | `/gazette?limit=10` | Newest-first array; limit 1..30 (422 otherwise) |

Gazette edition: `{id,village_id,edition_date,created_at,model,ai_generated:true,content}`.
Content: `{label:"AI-generated Village Gazette",headline,stories,gossip,weather}`.
Stories contain `text`, `source` and optional `source_id`/`user_id`; gossip contains
`text` and nullable `target_user_id`. Weather is a recorded fictional village forecast,
not a real-world weather service. All names, excerpts and story text are untrusted
display data; render as text, never HTML.

## Memory policy

`mayor_memory` stores one bounded JSON document per village. Transactional database
triggers refresh it after weekly finalization, Mayor event insertion/status changes,
and check-ins. Migration also initializes pre-existing history. No summarization
provider calls are needed. Weeks retain up to four recent finalized results, with
winner and completed-goal counts. Per-member facts retain lifetime weekly wins,
check-in counts and repeated evidence-key counts. Reused evidence is an observation,
not an accusation of cheating. Recent summaries retain prayer responses, recaps and
event outcomes. Raw source history remains intact when the compact view evicts data.

The stored document is at most 1,400 UTF-8 bytes. The prompt projection also bounds
ASCII-escaped JSON to 1,400 bytes, conservatively below 1,500 byte-level model tokens.
Compaction removes older entries, prioritizing at least one entry per category when
space permits. At most 12 villagers are considered in house-slot order; very large
villages can lose tail facts under this hard budget. No claim of semantic fact
extraction from photographs is made. Structured counters are grounded in records.

Every real `Mayor.generate` invocation loads village memory using the authenticated
village context, unless the caller already supplied bounded memory. This keeps the
existing list-valued activity context compatible with the iMessage adapter. Prompts
without village context receive empty memory. Provider instructions treat all memory
and source records as untrusted data. UUID facts resolve through the village roster.

## Event mechanics

The LLM selects an explicit template and fills its title/body. Server validation runs
both during schema parsing and immediately before persistence. Unknown/missing
templates, mismatched penalties, invalid kinds and out-of-range rewards are rejected.
Too few village members also rejects the proposal. Prayer failures produce a zero-XP
encouragement; scheduler failures perform no event action. Recaps have no effects.
Existing fixture/repair records are preserved and need no retroactive template.

| Template | Tier / members | Effort hours | XP per recipient | Penalty |
| --- | --- | --- | --- | --- |
| small_step | solo / 1 | 0.25 | 25..50 | none |
| buddy_chat | pair / 2 | 0.5 | 50..80 | fog |
| game_night | group / 3 | 1 | 80..120 | sad_pet |
| village_project | group / 3 | 2 | 120..200 | crater |
| weekend_build | group / 3 | 4 | 200..300 | house_downgrade |
| encouragement | solo / 1 | 0 | 0 | none |

Challenge/random-event deadlines are seven days. Penalties are cosmetic village
flags, never asset removal or negative XP. Existing failure handling makes a linked
repair challenge and fog; completing that repair clears the effects projection.
The existing owner-audited completion route still decides recipients and awards XP
once per recipient. Effort/participant activity is human-attested, not automatically
verified. New event creation responses include `template_id`; existing village event
projections remain compatible. Web should use the template and effects endpoints to
render difficulty and sad-pet/house flags; it must not infer permanent inventory loss.

## Gazette policy and reasonable choices

One edition per UTC date per eligible village, published on the first scheduler tick
of that day. Existing QA and 48-hour human-activity exclusions remain. Scheduler must
be enabled; GET endpoints never generate or spend money. Publication uses a dedicated
transaction and per-village advisory lock plus a unique date key, so concurrent workers
do not duplicate generation. A later scheduler-decision failure cannot roll back the
already-published newspaper. Provider failure/budget exhaustion publishes a clearly
marked fallback edition, with no repeated daily attempts. Process termination before
commit can still cause a subsequent attempt; the existing global physical-call budget
remains the hard spending ceiling.

The model edits by selecting/ordering 3..5 real story keys, a vetted headline and a
consenting gossip subject/style. The server renders recorded facts/excerpts instead
of trusting invented narrative assertions. Sources include today's check-ins, latest
competition statuses and permanent unlocks; quiet days use truthful zero-count
summaries rather than fabricated news. `model` records actual provider/model provenance
or `fallback:gazette-v1`. Gazette is deliberately a constrained newspaper editor,
not an unconstrained factual reporter.

Roasts use vetted, mild server templates. Unknown/nonconsenting targets cause fallback.
Every historical read rechecks current membership and `roast_ok`, replacing revoked
roasts with town-hall kettle gossip. No LLM-written roast can smuggle in a second target.
All adapters still use the existing global hourly budget for physical calls, repairs
and provider fallback. No real paid calls were made during implementation.
