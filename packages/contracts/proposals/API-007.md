# API-007: village world and group-photo onboarding

Integrator proposal only; shared `api.md`, `schema.sql`, web and GPU code are unchanged.
Apply `apps/api/migrations/006_world_group_photo.sql` before deploying this API.

## Web routes

All routes require authentication and membership in `{vid}`. Prefix: `/api`.

| Method | Route | Request / response additions |
| --- | --- | --- |
| GET | `/villages/{vid}` | Adds `world` below; events add nullable `repairs_event_id` |
| GET | `/villages/{vid}/shop` | Items add `requires_building` and `requires_item`; `requires` is building ID when present, otherwise item ID |
| POST | `/villages/{vid}/shop/buy` | Existing `{item_id}`; 409 if required building is locked |
| POST | `/villages/{vid}/group-photo` | Owner only; multipart `file`, `consent=true`; returns `{job_id}` |
| GET | `/villages/{vid}/group-photo/{job_id}` | `{job_id,status,error,crops:[{crop_id,url,claimed_by}]}` |
| POST | `/villages/{vid}/group-photo/{job_id}/claim` | `{crop_id}`; returns `{crop_id,user_id,job_id}` where job_id is the caller's head job |
| POST | `/villages/{vid}/events/{eid}/complete` | Existing owner-only `{user_ids:[uuid]}`; completing a linked repair removes its crater/fog |
| GET | `/assets/group-photos/{vid}/{job_id}/{file}` | Authenticated village-member access to stored photo/crops |

Example world for the reset demo:

```json
{
  "level": 4,
  "xp": 2800,
  "next_level_xp": 5000,
  "unlocked": ["garden", "festival_lights", "pet_shelter"],
  "upcoming": [
    {"building": "ferris_wheel", "level": 5, "xp": 5000},
    {"building": "lake_bridge", "level": 6, "xp": 8000}
  ],
  "weather": "fog",
  "time_of_day": "day"
}
```

Time is UTC: day 06:00–17:59, night otherwise. Thresholds: L1=0, L2=500,
L3=1500, L4=2500, L5=5000, L6=8000; L6 has `next_level_xp:null`.
XP sums positive lifetime ledger awards in this village for its current members.
Event awards already reside in that ledger and count once; purchases/negative entries
never reduce world XP. Unlocks persist, even if future membership changes lower XP.
`upcoming` lists still-locked buildings in threshold order. `pet_dog_b` costs 100 XP
and requires `pet_shelter`; existing `pet_dog` retains its backyard prerequisite.

Growth materializes on village reads, building-gated purchases, event completion and
eligible scheduler ticks. A unique `(village_id,building)` record gates both one
`building_unlocked` activity and one Mayor `agent_decision` announcement. No paid call
or outbound message is needed for announcements; `/feed` and `/agent-log` expose them.

Scheduler `MayorDecision` adds `action:"weather"` and optional enum `weather`:
`clear|rain|fog|festival_night`. Changes serialize per village and require three hours
since the prior accepted change; identical choices do nothing. Accepted changes log
the reason. Failed events with penalties get a unique zero-XP, nonexpiring repair
challenge. Overdue active non-recap events become failed on reconciliation. An unresolved
repair overrides scheduled weather with fog; completing the repair restores scheduled
weather. Failure/repair transitions are exempt from the scheduler's weather cooldown.
Multiple unresolved repairs keep fog until all are complete. Original failures remain
historically failed. Cosmetic crater visibility comes from the active repair event;
completion removes that event from `active_events`. Houses are not destructively changed.

## Group-photo semantics and errors

Owner upload consent attests that everyone pictured consented to processing. Claim is
an explicit self-onboarding action. No face recognition or automatic identity assignment.
Duplicate normalized image bytes in one village return the same segment job. Membership
is checked on every poll/claim/asset request. Jobs from another village return 404.
Queued/running/failed jobs return no crops; failure text is sanitized. Missing consent
is 422; non-owner upload/nonmember access is 403. Invalid image behavior matches the
existing single-photo upload (JPEG/PNG/WebP, normalization and safety size limits).

One crop per member and one member per crop **within each group-photo job**. Concurrent
claims serialize under the job row lock, with database uniqueness as a second guard.
The same member claiming the same crop again returns the original head job; conflicts
return 409. Unknown crop is 404; unfinished segment or invalid/missing artifacts is 409.
No user ID is accepted in a claim body. A member with another active personal avatar
pipeline receives 409; retry when it finishes. A later group photo can onboard again.

The API verifies crop keys stay under this job's `group-photos/{vid}/{job_id}/` namespace,
resolves them inside ASSET_DIR, and checks files exist. Claim decodes the crop, writes
`avatars/{uid}/face_512.png`, then enqueues `head` with `face_asset_key`, `sha256`,
`source_job`, `crop_id`, `user_id`, `consent:true`. Existing bridge head success/failure
paths enqueue body. No LLM, voice or GPU work occurs on polling.

## Required GPU bridge integration (deployment blocker for real group uploads)

Current `workers/gpu/bridge.py:do_segment` ignores group flags, selects one person,
mutates the uploader's avatar and starts head generation. Its result omits the crop
list. **Deploy the group-aware bridge change before enabling these routes against
the shared worker.** Do not send real group uploads to the old bridge. This API work
does not modify or restart that bridge; tests emulate its required output offline.

API segment input:

```json
{
  "asset_key": "group-photos/<vid>/<job_id>/<upload>.png",
  "photo_asset_key": "group-photos/<vid>/<job_id>/<upload>.png",
  "sha256": "<normalized-image-digest>",
  "user_id": "<owner-uuid>",
  "village_id": "<vid>",
  "group_photo": true,
  "protocol_version": 1,
  "output_prefix": "group-photos/<vid>/<job_id>",
  "auto_enqueue_head": false,
  "consent": true
}
```

For `group_photo:true`, bridge must run segment in a job-specific output namespace,
retain every person's face PNG, avoid writing the owner's canonical face/manifest,
avoid head/body generation (including the failure path), and finish the segment job
with this result, only after all files exist in shared ASSET_DIR:

```json
{"crops":[{"crop_id":"person_0","face_asset_key":"group-photos/<vid>/<job_id>/person_0.png"}]}
```

Crop IDs must be unique `[A-Za-z0-9_-]{1,100}`. Empty crops may be returned for no people.
The existing worker segment response has crops, but the bridge currently discards them;
worker output isolation may also need adaptation. Old-bridge completed jobs return a
specific 409 on polling instead of falsely presenting a complete group flow.

## Storage / migration proposal

Migration 006 is additive, idempotent UTF-8 without BOM. Adds `village_world`,
`village_unlocks`, `group_photos`, `group_photo_claims`; nullable catalog
`requires_building` preserves the existing item-only `requires` FK. Adds nullable
`mayor_events.repairs_event_id` with unique index. Associations cascade with the village;
global user/avatar/job rows remain untouched by demo reset. File and SQL commits are
not atomic: failed commits/process crashes can leave stored images for later cleanup.

`demo_story.py` upgrades an existing story once without discarding progress, then is a
strict no-op. `--reset` rebuilds the fixed demo village at level 4, with its original
aftermath linked as the repair. No new avatar jobs or paid calls are seeded.
