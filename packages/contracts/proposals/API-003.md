# API-003 proposal: weekly audits and opt-in competitions

Implementation lives on `api/API-003`; shared `api.md` and `schema.sql` are unchanged.
Apply `apps/api/migrations/003_audits_competitions.sql` after the shared schema. The API
migration script now does both, transactionally and idempotently. No existing columns change.
Migration was exercised only in `village_test`; deployment to the shared DB is outstanding.

## New tables

- `weekly_audits`: unique village/UTC Monday; auditor, generation, status, winner, finalization time.
- `weekly_assignments`: all people assigned in a week; excludes them from that week's competition.
- `weekly_grades`: unique week/goal, human auditor, three bounded integer scores, completed, rationale.
- `weekly_suggestions`: cached AI score/rationale JSON and model provenance, unique week/goal.
- `weekly_votes`: unique week/generation/voter, preventing duplicate or stale removal votes.
- `weekly_badges`: one completion star per week/user.
- `auditor_penalties`: removed auditor's pet-sad flag, automatically expires after seven days.
- `competitions`: immutable terms, creator, auditor/mode, lamport entry intent, fee bps, settlement JSON.
- `competition_participants`: self-opt-in and accepted entry intent per competition/user.
- `competition_entries`: immutable submitted claim/photo/key, AI review, human decision/points/reason.

XP remains in `xp_ledger`, and all mutations log to `activity_events`. AI work uses
`type=agent_decision`, so the existing `/agent-log` exposes it without a separate log table.
There are no wallets, chain clients, transfers, fee collection, or signed transactions.

## Routes for the web lane

All paths below are relative to `/api/villages/{vid}` and require authenticated membership.
Dates are ISO UTC Mondays. Errors: 403 role/membership, 404 missing resource, 409 state
conflict, 422 invalid body/date/evidence. OpenAPI includes all request schemas.

| Method | Path | Body / response |
| --- | --- | --- |
| GET | `/weekly/current` | Initializes this week's random auditor once; returns WeekState |
| GET | `/weekly/{week_start}` | WeekState; historical week must already exist |
| POST | `/weekly/{week_start}/goals/{gid}/suggestion` | Auditor only; `{suggestion: Grade, model}`; cached by default, `?refresh=true` explicitly recomputes |
| POST | `/weekly/{week_start}/goals/{gid}/grade` | Auditor only; Grade body, returns stored grade |
| POST | `/weekly/{week_start}/finalize` | Auditor only; no body; WeekState, idempotent awards |
| POST | `/weekly/{week_start}/insufficient` | `{generation: number}`; WeekState |
| GET | `/competitions` | Competition[] newest first |
| POST | `/competitions` | CreateCompetition; returns CompetitionDetail |
| GET | `/competitions/{cid}` | CompetitionDetail with participants and entries/reviews |
| POST | `/competitions/{cid}/join` | No body; self-opt-in only; CompetitionDetail |
| POST | `/competitions/{cid}/entries` | EntryInput; returns entry (AI review initially null) |
| POST | `/competitions/{cid}/entries/{eid}/decision` | `{decision:"confirmed"|"rejected", points:0..500, reason:string}`; stored entry |
| POST | `/competitions/{cid}/settle` | No body; settled Competition with result; idempotent |

```ts
type Grade = {
  ambition: number; evidence_quality: number; progress: number; // integers 1..5
  completed: boolean; rationale: string; // 1..2000 characters
};
type CreateCompetition = {
  title: string; terms: string; friendly?: boolean; auditor_id?: string;
  entry_lamports?: number; // integer 0..1e12, intention only (1 SOL = 1e9 lamports)
  auditor_fee_bps?: number; // integer 0..10000, intention only
};
type EntryInput = {body: string; evidence_asset_id?: string; idempotency_key: string};
```

WeekState includes `id,village_id,week_start,auditor_id,generation,status,winner_id,finalized_at`,
`votes` for the current generation, `stars` (user IDs), and `goals`. Each goal has nullable
`suggestion` and `grade`, and `excluded` for anyone assigned auditor in that week.
Human grade includes `week_id,goal_id,auditor_id` alongside Grade fields. AI suggestion is
advisory and never automatically creates a human grade. To accept it, POST its Grade fields;
to edit it, change those fields first. Grade `completed` is independent of self-reported goal status.

CompetitionDetail includes the competition row, `participants` (user IDs and entry intent),
and `entries` with `review:{verdict,confidence,reason,model}|null`. Entry evidence uses the
existing private upload endpoint and ownership record; display via authenticated
`/api/assets/{evidence_asset_id}` fetch. Poll the detail route for asynchronous AI review.
Settlement `result={winners:string[], scores:{user_id,points}[], payments_executed:false}`.

Existing Villager gains `star_badges:[{week_start,kind:"star"}]` and `pet_sad:boolean`.
`has_crown` belongs only to the latest finalized week's winner after a weekly result exists.
Before then, legacy equipped crown behavior is preserved. A later no-winner week clears the crown.

## Policy choices and limits

- Weeks initialize lazily on GET, requiring at least two members. No consecutive-week reuse
  of anyone assigned last week. If no eligible member exists, auditor_id is null; grading and
  finalization are unavailable. An unassigned initialized week remains unassigned until next
  week; enlarge the village before initializing. No scheduler or paid calls on GET.
- All assigned auditors, including removed auditors and replacements, sit out the whole week.
  All eligible goals must be human-graded before finalizing. Finalization is explicit and can
  be exercised early for the hackathon; it also supports a previously initialized past week.
- Only `completed=true` eligible goals can win or earn stars. Highest sum of the three rubric
  scores wins 100 XP; a tie uses ascending user UUID for one deterministic crown. No completed
  goals means no winner. Awards and stars persist, crown follows latest finalized week.
- Editing a current goal invalidates its cached suggestion and human grade. Finalized weeks
  reject title/detail goal upserts. Later goal-status/check-in changes do not revise awards.
  Suggestions use the latest 100 goal-linked check-ins in that week's UTC interval and each
  check-in's latest evidence review; explicitly refresh after new evidence arrives.
- Removal needs strictly more than half of current village members (including the auditor in
  the denominator). Auditor cannot vote. This means two-member villages cannot remove an
  auditor through this majority policy. Votes are per generation; stale votes return 409.
  Replacement is random among never-assigned members of this week, and all human grades
  reset for review. If no replacement remains, the triggering vote rolls back with 409.
- Competition creator does not opt others in or automatically enter. Audited competitions
  use a specified village member or random non-creator auditor at creation. That auditor
  cannot join. Terms, fees, and auditor cannot change after creation.
- Audited entries require the submitting member's photo; shared VLM review runs after response
  commit. Human confirmation is authoritative even when the AI rejects/errors. Rejected
  entries must have zero points. Pending entries block settlement; confirmed entries sum to
  scores, tied positive leaders all win. Each participant earns their score as XP, capped at
  500 per competition; empty/all-zero competitions settle without winners.
- Friendly competitions enforce zero stake/fee and no auditor. Self-reported entries earn
  one scoreboard point apiece; creator settles. They grant no spendable XP. This keeps the
  mode useful offline without opening unverified XP farming.
- Review tasks are in-process, not durable jobs. Replay the same entry/key before settlement
  to recover a missing review after a process crash. Completed AI failures remain visible;
  human review can proceed. Stored human decisions cannot be overwritten by a late AI result.
- Generation errors return conservative suggestions or review error objects. Raw provider
  error messages and credentials are never stored. Weekly suggestion generation holds the
  village row lock for consistency, so slow providers can briefly delay weekly/goal mutations.

## DeepSeek compatibility

OpenRouter receives JSON schema plus a concrete mode-specific example. The adapter accepts
Markdown fences, one common object wrapper, common field aliases, decimal-string reward XP,
and `none`/`null` strings for penalty. It preserves reward bounds, strict scores, unknown-field
rejection, and enum restrictions. Only validation/JSON errors get one repair request carrying
sanitized validation errors; transport errors immediately follow existing provider fallback.
Five explicit synthetic live trials passed: pray, recap, nudge, pray, recap (5/5, 100%).
This is a small smoke sample, not a production reliability estimate.
