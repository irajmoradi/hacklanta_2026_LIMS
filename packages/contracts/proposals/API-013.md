# API-013: playful face check after login

These are proposed additive HTTP/schema contracts; the canonical contracts remain unchanged.
All endpoints use existing Auth0 bearer authentication or configured demo authentication.
Face recognition is optional and is never used to authorize another API route. It is not
liveness detection: a photo of a photo can pass.

## Routes

| Route | Input | Success |
| --- | --- | --- |
| `POST /api/auth/face-verify` | Multipart `file`: JPEG/PNG/WebP, at most 8 MiB | `{ "match": true, "face_found": true }` |
| `POST /api/auth/face-enroll` | No body required; uses existing worker avatar photo | `{ "enrolled": true, "face_found": true }` |
| `GET /api/me` | Existing authentication | Existing response plus `user.face_verified_at`: ISO timestamp or null |
| `PATCH /api/me` | Existing profile fields | Same additive user field as GET |

Neither POST accepts a target identity or threshold: extra client fields cannot change the
authenticated user's identity. Verify forwards only that identity, the uploaded bytes with
a generic filename, and threshold `0.40`. Enroll forwards JSON `{user_id: caller_id}`.
Worker URLs accept a base URL or the existing `/health` configuration.
The worker may automatically refresh enrollment when its source avatar photo changes.

## State and badge

- A match with a detected face stamps `users.face_verified_at`. `/me` projects null once it
  is five minutes old. A new match refreshes it. Failed checks leave the prior TTL unchanged.
- Successful explicit enrollment clears the flag, requiring a fresh verification.
- A successful check records the badge in `xp_ledger`, reason **Recognized by the village**,
  global idempotency key `face-recognized:<user_id>`, delta **0**. This marks recognition
  without changing competition scores. The usual XP activity event is emitted once.
- The ledger requires a village. Use the earliest joined current village, ordered by ID on
  ties. A user with no village can verify; their badge is deferred until a successful check
  after joining. No cross-user award is possible. As with other ledger entries, deleting the
  village cascades its history; a later check can record the badge in another village.
- Migration `apps/api/migrations/013_face_auth.sql` is additive, repeatable and UTF-8 without BOM.

## Limits, errors and privacy

- Both POSTs share five attempts per rolling minute per authenticated user. PostgreSQL row
  locks coordinate processes; reservations commit before worker I/O and count worker failures
  and bad uploads even when subsequent work rolls back. This also commits a newly authenticated
  Auth0 user before processing their selfie. `429` includes `Retry-After` seconds.
- `face_auth_limits` stores at most five attempt timestamps per identity, with no image data.
  Its user FK cascades on account deletion. Reservations reuse the request connection to avoid
  exhausting the connection pool under concurrent requests.
- Selfies are parsed in bounded memory, including uploads above Starlette's normal disk spool
  threshold, closed after parsing, and forwarded without writing assets, DB image data, or logs.
  Multipart overhead is limited to 64 KiB; at most one file and four text fields are allowed.
- `401`: login required; `413`: too large; `415`: unsupported media type;
  `422`: missing/malformed file or no usable enrollment face; `404`: upload an avatar first.
- Unreachable worker, timeout, unsuccessful unexpected HTTP status, or malformed response:
  `503` with a friendly retry message. Raw scores, model data, filenames and worker error
  details never appear in responses. Worker-side cleanup is defined by CV-007.
- Worker unavailable does not block ordinary login or `/me`. No paid models are called.

## Teammate verification

From `apps/api`, set `VILLAGE_ENV_FILE` to the shared root `.env` path at runtime. Run
`python scripts/migrate.py`, then start the usual API server with the Windows selector loop
when needed. After login, POST a selfie using multipart field `file`, then GET `/api/me`.
To refresh from a new processed avatar photo, POST `/api/auth/face-enroll` with no body.

Automated checks: `python -m pytest tests/test_api013.py -q` uses mocked worker HTTP and an
isolated schema in `village_test`; it does not send personal images or invoke real models.
No UI changes or screenshot are part of this task.
