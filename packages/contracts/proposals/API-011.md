## Photo items

All routes require authentication and membership; paths below have `/api` prefix.

| Method | Path | Shape |
| --- | --- | --- |
| POST | `/villages/{vid}/items/from-photo` | Multipart `file`, `kind=outfit|object`, `consent=true`; outfit requires `slot=torso|head`; optional `prompt`. 202 `{id,status:"queued",item:null}` |
| GET | `/villages/{vid}/items/jobs/{id}` | Owner-only `{id,status,error,item}`; 404 for another member's job |
| GET | `/villages/{vid}/items` | Owner-only `{photo_item_tokens,items}` |
| POST | `/villages/{vid}/items/token` | Buy one token for registry price; 201 `{id}`. 404 unless `photo_item_token` exists in the runtime registry with a shop tag and synced catalog row |

Prompt is the CV-006 noun pattern `[A-Za-z][A-Za-z -]{0,39}`. False consent,
missing outfit slot, object with outfit slot, and invalid prompt return 422.
Existing image validation, size limits, and canonical private upload storage apply.
No token returns 409 before saving an image or queuing work. Insufficient XP returns
409. Jobs enqueue the exact CV-006 `input.kind`, `photo_asset_key`, `user_id`,
`consent`, optional `slot`/`prompt`, and `stage=segment` in `avatar_jobs`.
There is no API-side GPU call, polling loop, or provider generation loop.

`photo_item_tokens` grants one durable, single-use token per finalized weekly crown
and positive Mayor event XP award. Database triggers cover existing weekly/event
routes, including explicit prayers and scheduler events. Unique source keys prevent
duplicate grants. Migration backfills historical rewards of current members without
restoring spent tokens on replay. The dedicated purchase route supports repeat token
purchases and enforces existing requirements and the XP balance under member locking.
The current registry has no token SKU; no catalog files were changed for this task.
Frontend must use this dedicated route for consumables, not generic `/shop/buy`.

Creation consumes one token atomically with job insertion. Concurrent submissions
cannot spend the same token. A failed job keeps its spent token: the rule is one
token per creation, with no automatic refund or paid retry. POSTs have no client
idempotency key; do not automatically retry an ambiguous successful submission.

The first successful status/inventory read materializes a unique custom item from
the completed worker result. Reads never start generation. Malformed worker output
returns 502 without creating an item: kind/slot/tint must match, and assets must be
canonical PNG/GLB URLs inside that job's owner directory. Repeated/concurrent reads
return the same item. Legacy CV-006 example jobs are not silently adopted as free
inventory; only jobs queued through this rewarded flow are linked to a village.

Custom item shape:
`{id,village_id,owner,kind,slot,tint,pattern_url,glb_url,preview,source_job,equipped,created_at}`.
Outfits contain primary/secondary hex tint and pattern; objects contain the metric
GLB and `slot=decoration`. Use existing `/inventory/equip` and `/inventory/unequip`
with the custom UUID string as `item_id`. Catalog and custom equipment share slot
exclusion in both directions, including catalog purchases. Village villager rows
include these items in `equipped`/`equipped_ids`, with `custom:true`, appearance URLs,
and object `placement:"house_decoration"`. The enclosing villager's `house_slot`
identifies the yard; the client places the grounded 0.6m CV-006 prop at its existing
house decoration anchor. No arbitrary client world coordinates are accepted.

`/api/assets/items/<uid>/<job>/...` allows the owner and current village peers using
the existing confined asset path and peer authorization. Source uploads remain private.

## Event pack projection

Village payload `world.active_pack` is null or a registry/template pack definition
plus `{event_id,ends_at}`. Select the newest eligible active, unexpired, non-repair
event with a matching pack. An explicit vetted template `pack` may be a definition
or registry ID; otherwise the event template ID matches an `event_packs` registry ID
(e.g. `game_night`). Both registries without this section and the additive ARCH-003
section work. No hardcoded new pack names or assets are required.

Pack weather overrides the ordinary projected weather only for that event window.
Completion, failure or expiry removes it immediately and restores current ordinary
weather, including repair fog. This is derived state, not a persistent weather write;
it avoids stale timed effects and does not reset the weather cooldown. Pack weather
takes precedence over repair fog while a qualifying pack event is active.

`world.py` is outside this task's allowed paths. `photo_items.register` composes the
existing village endpoint at router registration, preserving its auth/dependencies,
and applies `scheduler.project_event_pack` to the returned world object. Other
routes are registered unchanged; no global monkeypatch or response/SSE buffering.

## Gazette investigation and proof

Read-only inspection of the development database found the Oct 10 issue stored as
`fallback:gazette-v1` at **10:25:10 UTC (06:25 EDT)**. The status log's manual publish
was at 06:40. `publish` returns any existing daily edition before contacting a
provider, so the manual call returned that cached fallback. Hourly provider usage
at 10:00 UTC was 7 against the configured limit of 60; budget exhaustion is not
supported by this evidence. The original swallowed exception was not retained,
so its exact provider/schema cause cannot be recovered or honestly asserted.

The prompt now explicitly requires exact fact keys and the GazetteDraft JSON shape.
Failures log only exception class, never provider bodies, source text or secrets.
Content includes `provenance:{model,fallback_reason}`. Validated factual stories and
current gossip consent checks remain intact. Existing provider/model provenance is
still recorded in the edition's `model` field.

An operator can explicitly call
`await newspaper.publish(conn, settings, vid, retry_fallback=True)` to replace a
cached fallback in place, retaining edition ID. The same advisory lock serializes
repairs; an already successful issue is never regenerated by this flag. Default
scheduler publication and GET routes do not retry or spend again for that date.
No public generation endpoint or recurring paid retry was introduced.

One authorized real generation was performed using external env values at runtime,
synthetic fixture context and the isolated test database. Result:

```text
API011_LIVE calls=1 model=deepseek/deepseek-v4-flash:gazette-v1
provenance={'model': 'deepseek/deepseek-v4-flash', 'fallback_reason': None}
1 passed in 1.91s
```

The opt-in proof guards all physical attempts (including provider repair/fallback)
at two calls. Only **one** was used for this task. The live development issue and
service were not modified. Ordinary tests mock providers; the proof is skipped
unless `API011_LIVE_GAZETTE=1` is explicitly set. The proof does not claim that all
future provider requests will succeed or that the original failure was reproduced.

## Integration limits and proposed contract changes

- Adopt the new tables, four routes, custom equipped fields, active pack projection,
  and Gazette provenance in shared contracts and consuming web code.
- ARCH-003/catalog owners may add the `photo_item_token` shop SKU and more template
  pack mappings. No catalog edits were made in this task.
- Account deletion already cascades custom DB ownership, but its filesystem cleanup
  currently lists only uploads/avatars/voice/evidence. The account owner must add
  canonical `items/<uid>` cleanup; `account.py` is outside allowed paths. Deleted
  users' leftover files are inaccessible via the peer asset route.
- Existing generic avatar generation-status reads include all segment jobs. They
  should exclude CV-006 item kinds when projecting avatar readiness. Changing
  `domain.avatar` is outside the allowed equipped-custom-items-only edit scope.
- No web UI was changed or visually tested. Screenshot: not applicable.

Changed files: `apps/api/app/photo_items.py`, `main.py` (asset rule and registration
only), `domain.py` (custom equipment only), `newspaper.py`, `scheduler.py`,
`apps/api/migrations/011_photo_items.sql`, `apps/api/tests/test_api011.py`, and this
proposal. No secrets, real photos, generated assets or model weights are committed.
