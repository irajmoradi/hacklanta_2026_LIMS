# CV-005: Group-photo onboarding (bridge/worker side). Shapes for API-007.

There are two job shapes, and both use the existing `avatar_jobs` table with `stage='segment'`. Nothing changes in the schema.

## 1. Group-photo segment job (enqueued by `POST /villages/{vid}/group-photo`)
```jsonc
// avatar_jobs row
{ "user_id": "<uploader uuid>",            // village owner who uploaded the photo
  "stage": "segment",
  "idem_key": "sha256(<vid>:<photo sha256>:group_segment:sam3:v1)",   // suggestion
  "input": {
    "group_photo": true,                   // REQUIRED flag: selects the group path
    "village_id": "<vid uuid>",            // REQUIRED
    "photo_asset_key": "villages/<vid>/group/<file>.jpg",  // REQUIRED, key relative to data/assets ("asset_key" also accepted)
    "sha256": "<photo sha256>",            // optional
    "consent": true, "user_id": "<uploader uuid>" } }
```
The bridge runs SAM 3 on the photo and writes **every** person crop (score > 0.5, area > 2% of image), sorted left to right:
```
data/assets/villages/<vid>/group/<job_id>/segment.json
data/assets/villages/<vid>/group/<job_id>/<crop_id>/{full_body.png, face_512.png, traits.json, masks/*.png}
crop_id = person_0, person_1, ... (left to right)
```
On success the job becomes `status='done'` with this result:
```jsonc
{ "group_photo": true,
  "village_id": "<vid>",
  "image_size": [w, h],
  "crop_count": 5,
  "crops": [
    { "crop_id": "person_0",
      "score": 0.938, "area_frac": 0.1071,          // SAM 3 person score, fraction of the image
      "box_xyxy": [x0, y0, x1, y1],                  // in original-photo pixels (to draw a picker overlay)
      "face_found": true,                            // false = face crop is a heuristic (top of body box)
      "colors": {"hair": "#…", "shirt": "#…", "pants": "#…", "shoes": "#…", "skin": "#…"},
      "full_body_url": "/api/assets/villages/<vid>/group/<job_id>/person_0/full_body.png",
      "face_url":      "/api/assets/villages/<vid>/group/<job_id>/person_0/face_512.png",
      "traits_url":    "/api/assets/villages/<vid>/group/<job_id>/person_0/traits.json" } ],
  "timing_s": { "model_load": 0.0, "person": 0.23, "total": 5.4 } }
```
- The group job does **not** write any avatar manifest, and it does **not** enqueue head/body jobs.
- With zero people found, the job fails with `error="no person found in the photo"`.
- **API-007 must add an asset rule.** Keys `villages/<vid>/...` should be readable by members of `<vid>` (`require_member`). Today `/api/assets` only
  serves those keys if a manifest references them exactly.

## 2. Per-member job (enqueued by `POST /villages/{vid}/group-photo/{job_id}/claim {crop_id}`)
```jsonc
{ "user_id": "<claiming member uuid>",
  "stage": "segment",
  "idem_key": "sha256(<member>:<group_job_id>:<crop_id>:claim:v1)",   // suggestion
  "input": {
    "group_job_id": "<uuid of job 1>",     // REQUIRED: must be a done group segment job
    "crop_id": "person_2",                 // REQUIRED: ^person_[0-9]+$, must be in that job's result.crops
    "village_id": "<vid>",                 // REQUIRED: must equal the group job's village_id
    "user_id": "<member uuid>", "consent": true } }
```
The bridge does **not** re-run SAM 3. It copies that crop's `full_body.png`, `face_512.png` and `traits.json` to
`data/assets/avatars/<member>/` and writes a manifest revision exactly like a normal segment:
`body.colors` from the crop, `portrait {kind:"photo", asset_url:/api/assets/avatars/<member>/face_512.png}`, `generation {segment:"ready", head:"queued"}`.
It then enqueues the normal chain: `head` (LAM) → `body` (Gemini + Hunyuan3D). The head idem key is
`sha256(<member>:<face_512 sha256>:head:lam20k:v1)`.
Result:
```jsonc
{ "manifest_revision": 1, "from_group_job": "<uuid>", "crop_id": "person_2", "selected_crop_id": "person_2",
  "colors": {...}, "face_url": "/api/assets/avatars/<member>/face_512.png", "head_job_id": "<uuid>" }
```
Errors are terminal job failures with short, safe messages: `group job not found or not done`, `crop not found in group job`,
`group job belongs to another village`.

## 3. Unchanged
A single-person upload (`POST /avatars/{uid}/photo`) keeps the old shape (no `group_photo`, no `group_job_id`).

## Implementation and test results (2026-10-10, live worker + bridge)
- Worker: `POST /segment/group` (multipart `village_id`, `group_job_id`, `file`) writes `assets/villages/<vid>/group/<gid>/…`. Crops now carry `box_xyxy`.
- Bridge: `do_segment` dispatches on `input.group_photo` (to `do_group_segment`) or `input.group_job_id` (to `do_claimed_crop`), and otherwise takes the old path.
  Group jobs never touch manifests, including on failure. A failed job no longer downgrades a stage that is already `ready` in the member's manifest.
- Tested by inserting `avatar_jobs` rows directly, since API-007's routes don't exist yet:
  - **Group job** on the CC0 crowd photo (2048 px) in the demo village: done in 24 s wall (including the 10.8 s SAM 3 load; 2.8 s of segmentation).
    It found **5 crops** (person_0…4; faces found for 0, 2 and 4). The uploader's manifest was untouched.
  - **Claim** of `person_2` by a temporary test user: done in **1.2 s** with no re-segmentation. The chain then ran: LAM head 50 s → body 197 s (cold loads,
    Gemini cache hit) → manifest `lam_head` + `head_glb_url`. The temp user, its rows and its files were deleted afterwards.
  - Errors: `person_99` gives `crop not found in group job`; a mismatched village_id gives `group job belongs to another village`; a missing photo gives `input asset missing`.
- **Fixture for API-007:** done group job `d5eca46a-2175-4915-8c3d-df1d040cea29` (demo village, uploader Iraj), with files under
  `data/assets/villages/13370000-0000-4000-8000-000000000000/group/d5eca46a-2175-4915-8c3d-df1d040cea29/`. It can be used to test
  `GET .../group-photo/{job_id}` and claim. Delete the row and that folder if you don't want it.
