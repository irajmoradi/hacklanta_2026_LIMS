# ACT-001 — External activity signals (Discord presence + Steam), read-only

Hackathon.pdf: "give it access to steam activity or discord activity … read only signal, honestly for status as well of
'this person played this game for this many hours' or weekly recap". Build a separate small service `apps/activity/`
(Python 3.12, uv) — it writes signals into the existing DB; the API/Mayor read them later.

1. **Linking**: table `external_accounts(user_id, provider: discord|steam, external_id, consent_at)` + `activity_signals`
   (hypertable: user_id, village_id, provider, kind: playing|listening|voice|online, title, minutes, started_at) —
   additive SQL in `apps/activity/sql/001_activity.sql` (idempotent, no BOM; the integrator applies it). A CLI
   `link.py --user <uuid> --discord <id> | --steam <steamid64>` (consent flag required).
2. **Discord**: discord.py gateway client with presences + members intents using DISCORD_BOT_TOKEN from the root .env;
   track games/Spotify/voice for linked users only, aggregate into sessions (start/stop → minutes). If the Presence intent
   is not enabled in the Developer Portal, log a clear message and exit 0 (the owner must toggle it). Never read message
   content. Do not disturb the existing bot connection used by Claude's Discord plugin (a second gateway session is fine).
3. **Steam**: if STEAM_API_KEY is set, poll GetRecentlyPlayedGames every 30 min for linked steamids (public profiles only)
   and record playtime deltas; otherwise skip with a log line.
4. Also write `village`-scoped `activity_events` rows of type `external_activity` ("Iraj played Minecraft for 2h") so the
   feed/Gazette pick them up, respecting a per-user opt-out flag.
5. Tests with fakes (no network): session aggregation, opt-out, unlinked users ignored. `README.md` with run commands.
   Do NOT start a long-running process at the end; just verify it starts and exits cleanly in a dry-run mode.
Final report per AGENTS.md.
