## Guard and evidence interpretation

The harness installs context-wide interception **before navigation**, blocks service workers, aborts every HTTP method except GET, and asserts that attempted non-GETs are absent. It allows actual WebSocket connections and incoming messages but drops all outbound application messages. No write exemption was made for seat leases, heartbeats, audio generation, or read receipts. No secrets or `.env` contents were needed. No application, contract, or live data was edited.

The app automatically attempts `POST /api/demo/seat`, presence heartbeats, and `scene-voice/mayor` when opening the Mayor with sound enabled. These are blocked, and therefore the strict safety test **fails**. The resulting `ERR_BLOCKED_BY_CLIENT` console messages, reconnect toast, and house “Live · connecting” status are **guard effects**, not evidence of a production outage. The audit does not certify server-synchronized movement, other users seeing movement, voice playback, or real reconnection under these restrictions. Keyboard input and reload recovery were exercised without transmitting movement.

Lab controls were inspected in `src/lab/sandbox.ts` and `WorldDemo.tsx`: they mutate an isolated in-memory fixture. All four local disaster cycles were exercised, with every +3 contribution recorded, without using live debug controls. The network guard stays installed in the Lab.

Screenshot photo/contact redactions are deliberate; colored or empty portrait boxes are not broken assets. Viewport captures preserve clipping and overlap. The broad mobile pass paused animation frames only during still capture; the final harness removes that optimization because it stalled privacy-aware follow-up captures. `step-duration` includes screenshots and deliberate waits, so it must not be reported as user-facing load latency. The shared runner uses software rendering. Only selected screenshots retained after privacy review are committed; the JSON records all checkpoints.

Raw per-surface text, navigation outcomes, HTTP failures, console errors, and blocked writes are in [desktop observations](../../apps/web/tests/screenshots/QA-014/desktop/observations.json) and [mobile observations](../../apps/web/tests/screenshots/QA-014/mobile/observations.json).
