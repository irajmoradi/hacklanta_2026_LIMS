# QA-012 — mobile, accessibility, keyboard, and first load

Audit dates: 2026-10-10–11 UTC (October 10 in America/New_York). Target: https://207-246-81-187.sslip.io.
Branch: `qa/QA-012`. Starting source revision: `2a493c6d8fec308ee51eddc0d3807a13ff22faa3`.
Scope: read-only report and evidence; no application or contract changes.

## Method and boundaries

- Playwright 1.58.2 / Chromium 145 on the configured remote runner, using the repository wrapper from `apps/web`. The wrapper serializes browser jobs across worktrees; queue time is not page load time.
- iPhone 14 at 390 × 844 / 844 × 390 and Pixel 7 at 412 × 839 / 839 × 412. This is Chromium emulation, not physical-device or Safari certification. Safe-area CSS inspection and a Chromium inset override complement the normal emulated geometry checks.
- All non-GET/HEAD/OPTIONS requests are aborted in the browser before reaching the network. This also blocks routine seat and presence heartbeats. No sends, uploads, generation, world changes, account changes, transactions, or server throttling are permitted by the harness. No secrets or environment values are needed for this demo-seat review.
- After the deployment changed, opening Check in attempted an automatic `POST .../scene-voice/checkin`. The guard blocked it. Scene voice behavior is therefore intentionally untested; any unavailable-voice state caused by this block is not a product finding.
- WCAG 2 A/AA and 2.1 AA axe scans use the installed `axe-core` dependency. Dialog checks record viewport and scroll geometry, close-button location after scrolling, ten Tab transitions, computed focus outlines, and Escape handling. Supplemental checks cover additional panels and keyboard navigation through town controls.
- Screenshots hide image elements, portrait renderers, WebGL canvases, telephone inputs, and conversation content. Blank scene areas and portrait slots are intentional redactions, not rendering defects. Axe runs before screenshot redaction.
- Performance uses fresh browser contexts with cache disabled and the existing Iraj seat preselected in local storage for both live and fixture modes, excluding human seat-choice time. The separate first-visit seat dialog is covered by the mobile sweep. “Interactive” means the town's Check in button is available and can open its dialog; it is not Lighthouse TTI or proof that every 3D asset has finished loading. Network byte totals are bounded observations, not the complete eventual download size. The runner uses SwiftShader software rendering and is shared; timings are not physical-phone benchmarks.
- Slow 3G is applied through Chromium's network emulation at 400 ms latency and 50,000 bytes/s download/upload. A separate slow-API experiment adds four seconds to API requests in browser routing only. The server is never modified.
- Source paths are suspected locations in this worktree. The deployed revision is not independently established and may change during the audit.

## Prioritized findings

No P0 observed. Status is recorded per finding because the shared target changed during this audit. Do not count historical or unconfirmed observations as current open bugs.

### QA-012-01 — P1: landscape dashboard covers the primary town actions

**Repro:** enter the village as an existing demo seat, leave the dashboard expanded, and rotate an iPhone 14 viewport to 844 × 390. Try tapping Check in and Village in the bottom dock.

**Observed:** the dashboard heading and chorus button extend into the dock. The “Everyone says it” button covers the first two actions; both Playwright pointer clicks time out. The screenshot shows the overlap without any injected layout changes. The remaining dock actions can still open.

**Evidence:** [landscape town](QA-012/town-landscape.png). Automated measurements and independent hit-testing are recorded with the final matrix below.

**Expected / impact:** primary actions remain reachable in short landscape viewports. Collapsing the dashboard or using keyboard activation is a potential workaround, not a substitute for touch access.

**Suspected files:** `apps/web/src/components/Dashboard.css` (`.dashboard` top/bottom constraints and `.dashboard-body`), `apps/web/src/components/Dashboard.tsx` (chorus outside the scrolling card list), and `apps/web/src/styles.css` (action dock). Consider a short-height layout and keep all dashboard content within its available scroll region.

### QA-012-02 — historical P1: profile content clipped; no longer reproduced after deployment

**Follow-up status:** the later live build changes the outer profile to `overflow-y:auto` and the tab body to `overflow-y:visible`. On iPhone portrait the outer panel now has a 2,081 px scroll extent, and both House editor and Customize my avatar open successfully. The earlier clipping evidence below remains valid for the initial sweep, but this is **not an open P1 on the follow-up build**. No application fix was made in this worktree.

**Repro:** at 390 × 844, open My profile for Iraj and inspect Overview, Outfit, House, Rewards, and Activity without playing or generating a voice line.

**Observed:** the voice studio occupies nearly the entire profile surface. The tabs are near the bottom edge and their content extends beyond the visible panel. The profile has 1,051 px of scroll extent inside an 844 px client height; scrolling the inner tab content does not bring the entire content area into view. Independent initial-layout measurements are included in the supplemental evidence.

**Evidence:** [portrait profile](QA-012/profile-portrait.png), [landscape profile](QA-012/profile-landscape.png). The blank face stage is privacy redaction; the excessive allocation of space and clipped content are the finding.

**Expected / impact:** the profile body should remain readable and scrollable with its close control reachable. This affects core profile and customization access on phones.

**Suspected files:** `apps/web/src/components/ProfilePanel.tsx` (HeadStudio before the tab list), `apps/web/src/components/HeadStudio.css` (non-shrinking studio, later changed to a full-width column), and `.profile-panel` / `.profile-tab-content` rules in `apps/web/src/styles.css` (flex column with hidden outer overflow and a shrinkable inner content area). Put the studio inside a scrollable body or collapse it on short screens.

### QA-012-03 — unconfirmed axe flag: AI log keyboard access

**Follow-up status:** this is **not a confirmed keyboard-access defect in tested Chromium**. A separate 24-Tab walk focused `.agent-log` twice, despite its DOM `tabIndex` being -1 and having no focusable children. Chromium supplies native scroll-container focus. Retain the axe finding as a Safari/assistive-technology compatibility lead; exclude it from confirmed P2 counts.

**Repro:** open AI at work after decisions load, then navigate only with Tab and scrolling keys.

**Observed:** axe reports `scrollable-region-focusable` on `.agent-log`. The iPhone portrait sample had 12,821 px of additional internal scroll content. The source does not add an explicit tab stop. The keyboard follow-up demonstrates that this alone does not prove keyboard inaccessibility in Chromium.

**Evidence:** [AI activity panel](QA-012/agent-log-keyboard.png); axe rule details in the audit JSON. Keyboard-only follow-up is recorded in the supplemental JSON.

**Next check:** verify Safari and assistive-technology access before filing a keyboard blocker. If those browsers cannot reach it, add an explicit tab stop, suitable accessible region semantics, and visible focus treatment.

**Suspected files:** `apps/web/src/components/AgentPanel.tsx` (`.agent-log`) and its overflow styling in `apps/web/src/styles.css`.

### QA-012-04 — historical P2: check-in reward captions fail text contrast

**Follow-up status:** the deployment replaced the original form with a cinematic Check in interface. Supplemental landscape scans on both devices and the initial recovery scan on iPhone portrait did not reproduce this contrast violation. The evidence below applies to the original interface, not a confirmed open failure in the replacement.

**Repro:** open Check in with Daily note selected. Inspect the XP/coin rewards under Daily note and Goal progress.

**Observed:** axe identifies four failing text nodes. Daily-note reward text is **3.60:1** (`#6a7b5e` over `#dde9cf`); the goal-progress coin caption is **3.78:1** (`#6c7c62` over `#e9eee0`). These are 11 px normal-weight captions and require 4.5:1. Disabled submit styling is not counted as this defect.

**Evidence:** [check-in captions](QA-012/checkin-contrast.png); `color-contrast` nodes in the audit JSON.

**Expected:** darken the reward caption colors or remove opacity that reduces contrast.

**Suspected files:** `apps/web/src/components/Modals.tsx` (`CheckInModal`), `Currency.tsx`, and `.segmented small` / reward styles in `apps/web/src/styles.css`.

### QA-012-05 — P2: competition error Retry button has very low contrast

**Repro:** open Compete when its read request fails or times out. This audit observed “The user aborted a request.” Do not trigger a write or world event to reproduce; a browser-only failure of the competition GET is sufficient for a controlled check.

**Observed:** the enabled Retry text is **1.64:1** (`#536348` over `#6b282e`, 10 px normal weight). The error itself is readable, but its recovery action is not.

**Evidence:** [competition error state](QA-012/competition-retry.png); the corresponding axe node is `p[role="alert"] > .text-button`. The cause of the read failure was not established; this finding is about the rendered recovery control, not a claim of a persistent API outage.

**Expected:** give recovery actions an explicit high-contrast color in the arena theme.

**Suspected files:** `apps/web/src/components/CompetitionsPanel.tsx` (error and Retry markup), `apps/web/src/components/colosseum.css`, and shared `.text-button` styles.

### QA-012-06 — P2: generic arena and portrait containers use unsupported accessible names

**Repro:** open Compete with competition details visible, or open My profile and switch tabs after the animated head becomes visible; run axe.

**Observed:** `aria-prohibited-attr` identifies `.arena-tabs`, a generic `div` with `aria-label="Arena status"`, and `.lam-canvas`, a generic `span` labeled as an animated head. Neither has a supporting role. Both landscape competition scans flag the first; all four Pixel portrait profile-tab scans flag the second. The later chorus/accomplishments scans additionally flag generic `.portrait-crown` spans labeled “Crown.” These are automated semantic findings; no screen-reader speech-output claim is made.

**Evidence:** the arena axe node in the audit JSON; the status row is visible in [the competition screenshot](QA-012/competition-retry.png).

**Expected:** use a suitable named grouping/region if a separate accessible name is needed, or remove the unsupported name from the generic container.

**Suspected files:** `apps/web/src/components/Colosseum.tsx` (`.arena-tabs`), `apps/web/src/components/GaussianHead.tsx` (`.lam-canvas`), and `apps/web/src/components/shared.tsx` (`.portrait-crown`).

### QA-012-07 — P2: bottom dock ignores a nonzero safe-area inset

**Repro:** in iPhone portrait emulation (390 × 844), use Chromium `Emulation.setSafeAreaInsetsOverride` with `{insets:{bottom:34}}`. Verify an independent `env(safe-area-inset-bottom)` probe resolves to 34 px, then inspect the dock. No application styles are changed by this test.

**Observed:** the dock still computes to `bottom:12px`; its bottom is 832 px and its buttons end at 821 px. The simulated safe region starts at 810 px, so the dock overlaps it by 22 px and the buttons by 11 px. The screenshot's orange strip is an explicitly labeled QA overlay indicating the simulated region.

**Evidence:** [safe-area simulation](QA-012/safe-area.png), `safeArea` in the supplemental JSON.

**Expected / limitation:** honor nonzero safe-area values when supplied. This is a verified Chromium environment-variable regression, not a claim that a physical Safari home indicator was tested.

**Suspected file:** `apps/web/src/styles.css`. The earlier `bottom:max(12px,env(safe-area-inset-bottom))` rule is overwritten by later action-dock rules using fixed 16 px / 12 px offsets. Retain the inset-aware offset in the final applicable rules.

Four additional Pixel portrait navigation attempts timed out. These are explicitly recorded, not counted as passes or automatically promoted to product bugs.
- All four touch-pan samples move the projected house labels, with page scroll staying at zero. Pinch increases projected spacing in iPhone portrait and both Pixel orientations while `visualViewport.scale` remains 1. The initial iPhone landscape pinch is inconclusive and has a separate canvas-only retest.
- The 34 px safe-area probe confirms QA-012-07. Normal zero-inset dock gaps were 12 px portrait and 16 px landscape. This does not substitute for physical Safari testing.
- Toast text was checked using a temporary DOM palette probe with the **deployed toast CSS**, without triggering an application event: title `#344831` / `#fffcf2` is **9.66:1**; detail `#67715d` / `#fffcf2` is **4.99:1**. Both meet 4.5:1. Delivery, lifetime, stacking, and live toast actions were not exercised.
- The AI-log axe flag is not reproduced as a Chromium Tab-access failure; see QA-012-03. The source remains worth checking on Safari, but it is not a confirmed current keyboard blocker.

The focused [iPhone landscape pinch retest](QA-012/screenshots/touch.json) passed with both initial touch points independently hit-tested as canvas: projected house-label separation increased **1.403×**, with `visualViewport.scale=1` and both page scroll offsets zero. This resolves the earlier inconclusive gesture sample. [Redacted retest screenshot](QA-012/screenshots/iPhone14-landscape-pinch-retest.png).

It produced no new evidence. The retained first attempt contains only one iPhone portrait replacement-Check-in scan, with no axe violations and a screenshot timeout. Do not interpret that partial result as a complete recovery run.

**Remaining coverage limits:** automatic reconnection after removing the API delay, latest-build controlled competition-read failure, Pixel portrait profile revalidation, and the nested camera-preview layout in all four viewports were not completed. The slow-API run proves the initial switch to Demo village, not whether it eventually reconnects. No check-in was submitted to either mode.
