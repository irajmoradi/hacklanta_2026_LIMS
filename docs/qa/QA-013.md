## Findings

**2 P1 and 5 P2 findings. No P0 was observed.** This is an audit of a changing live deployment, not a certification of a single frozen build.

### P1 - QA13-01: API outage can leave a completely blank application

**Judge in first 60 seconds: YES, if the interruption occurs during the demo.**

Observed sequence: select Iraj at 1440x900; open and close Members, Create new village, Friends, Reading list, Weekly review, then Gazette. During the Gazette/return-to-town sequence, production returned 41 HTTP 502 responses across avatar, village, profile, feed, unread-count, weekly-review and competition reads. The console then recorded `InvalidStateError: Failed to execute 'showPopover' on 'HTMLElement': Invalid on disconnected popover elements.` The application disappeared, including its navigation and recovery UI. Later clicks could not find the dock at all. No persistent write was involved.

Evidence: [blank application](QA-013/outage-blank.png), [original outage trace](QA-013/screenshots/outage.json). The stack identifies `/assets/index-GL81dqj_.js:227:10802`. A later read-only health probe returned 200 in 112 ms and a different entry bundle, `/assets/index-DKJ0aY70.js`. The subsequent cinematic run encountered another burst of 502s around 04:08:46-04:08:48 UTC but completed after recovery. A later client-only offline/Reading-list/Escape probe displayed reconnecting notices, kept `#root` mounted, and emitted no page exception; see [recovery trace](QA-013/screenshots/recovery.json). The earlier blank-page crash was **not reproduced in that later build/probe**, so it must not be represented as a guaranteed failure of the final deployment. Actual HTTP 502 bursts recurred separately during the audit. Interruption timing is external.

Suspected files: `apps/web/src/components/Toast.tsx:65` calls `showPopover()` in a ref callback without checking `node.isConnected`; its portal host is a dialog selected earlier by layout measurement. `apps/web/src/components/Reconnecting.tsx` creates the connection toast. Investigate the production API/reverse-proxy deployment lifecycle separately for the 502s. **Do not trigger a real outage to reproduce this.**

### P1 - QA13-02: New Bottoms and Shoes departments have no items

**Judge in first 60 seconds: YES if demonstrating the new wardrobe categories.**

Select Iraj > Shop > Bottoms, then Shoes. Both tabs select successfully but the item grid is empty, with no explanation or retry control. Glasses contains only the existing Round Glasses and can be tried on. The same result was observed at all three target sizes. This prevents the requested new bottoms/shoes previews; no buy or equip was attempted.

Evidence: [cinematic/shop cases](QA-013/screenshots/cinematics.json), each `shop.states` entry has `noTryOn: true` for Bottoms and Shoes. A separate healthy `GET /api/villages/13370000-0000-4000-8000-000000000000/shop` returned HTTP 200 with **64 items, zero `bottoms`, zero `shoes`, and one `face` item**; see `catalog` in [world trace](QA-013/screenshots/world.json). This confirms a catalog-content problem rather than a failed tab click. Screenshots: [Bottoms](QA-013/catalog-bottoms.png), [Shoes](QA-013/catalog-shoes.png).

Suspected files: `apps/api/app/main.py:497` (shop enumerates persisted `catalog_items`), `apps/api/app/catalog_registry.py:189` (`sync_catalog`), and `apps/web/src/components/Wardrobe.tsx:164` (empty filtered-grid fallback). The local catalog contains the new slots; do not hide the symptom by relabeling them as legacy slots.

### P2 - QA13-03: Mayor portrait loading text is clipped into fragments

**Judge in first 60 seconds: YES when opening Mayor before the portrait finishes loading.**

Open Mayor > What's new? On desktop the listener portrait displays fragments such as `LOADI / NG 3D / PORTR`; at 390x844 it shows only `L` in the small portrait. This is the loading status, not the redacted portrait image. The loading indicator should fit the compact portrait or be placed outside it. Loading duration is not claimed as a production performance defect because the runner uses software rendering.

Evidence: [desktop](QA-013/mayor-loading-desktop.png), [iPhone layout](QA-013/mayor-loading-mobile.png). Suspected files: `apps/web/src/components/GaussianHead.tsx:64`, `.head-shimmer` in `apps/web/src/styles.css:21` (16 px inset padding), and `.mayor-listener .portrait.large` in `apps/web/src/components/mayorScene.css` (44 px on mobile).

### P2 - QA13-05: Disabled debug capability produces console errors on normal entry

**Judge in first 60 seconds: NO in the normal UI; YES with DevTools open.**

Open the public site and select any demo seat. `GET /api/demo/debug` returns HTTP 404 and the browser logs "Failed to load resource." This repeats when changing seats. There is no corresponding user-facing failure; the debug controls correctly remain unavailable. Treat this as console noise, not a reason to enable debug actions in production.

Evidence: [normal town view](QA-013/town-console-404.png), `network` and `console` in [cinematic run](QA-013/screenshots/cinematics.json). Suspected file: `apps/web/src/components/DemoTools.tsx:19`; the capability probe runs on ordinary demo entry even when the endpoint is unavailable.


### P2 - QA13-06: Mobile header hides Settings and My profile without a scroll cue

**Judge in first 60 seconds: YES when looking for settings or their avatar.**

At iPhone 14 portrait (390x844), enter any demo seat and inspect the third header row before swiping. Testing-as, AI at work, Help and Inbox fill the row. Settings and My profile start outside the visible area, without a visible "More" control or scroll cue. On Lance, their left edges measured 387 px and 496 px respectively; the profile button ends at 540 px. The measured Iraj row is 366 px wide with 531 px of content.

This is **discoverability, not an inaccessible control**: a real emulated touch swipe from x=345 to x=100 at y=119 changes `scrollLeft` from 0 to 165 and exposes both controls. Suggested polish: provide a visible overflow cue or a compact menu. Evidence: [before swipe](QA-013/mobile-header-clipping.png), [after swipe](QA-013/mobile-header-after-swipe.png), [touch/geometry trace](QA-013/screenshots/panels.json). Suspected file: the WEB-051 mobile `.topbar-right` rules in `apps/web/src/styles.css:720`.


### P2 - QA13-07: Expanded mobile dashboard intercepts Gazette taps

**Judge in first 60 seconds: YES if they try the plaza notice board.**

Use Iraj at 390x844 with the default expanded dashboard. The Gazette sign is behind the Friends/Accomplishments/Reading-list strip. Clicking it cannot reach the scene button: Playwright repeatedly reports `.dashboard-social` or its Accomplishments button intercepting pointer events. In the targeted follow-up, the Gazette button occupied x=235.29, y=418.34, width=55.70, height=44, but the center hit-test returned `dashboard-social`.

Collapse the dashboard, then tap the same Gazette sign: the Gazette opens and Escape closes it. This workaround is verified, so the issue is an overlapping default layout rather than unavailable Gazette data. Evidence: [blocked view](QA-013/mobile-gazette-blocked.png), [opened after collapse](QA-013/mobile-gazette-after-collapse.png), [initial hit-target failure](QA-013/screenshots/panels.json), [geometry and successful workaround](QA-013/screenshots/dismissal.json). Suspected files: `apps/web/src/components/Dashboard.tsx:63`, mobile dashboard positioning in `apps/web/src/styles.css`, and the scene-label placement in `apps/web/src/scene/MayorPlaza.tsx`.

## Additional console and performance evidence

The clean seat matrix completed all 12 Lance/Stefanny/Maya/Mario viewport cases and recorded no blocked write attempts or screenshot failures. Maya (04:19:23 UTC) and Mario (04:21:30 UTC), in mobile contexts, nevertheless emitted `WebAssembly.instantiate(): Import #0 "env" "memory": mismatch in shared state of memory, declared = 0, imported = 1`. Navigation and the inspected panels continued working. See [seat trace](QA-013/screenshots/seats.json). Suspected area: `apps/web/src/components/lamRuntime.ts` / `packages/lam-renderer` and its decoder initialization. This remains a console/asset-runtime finding; the audit does not claim that the whole avatar failed or that it reproduces on physical iOS hardware.

The cinematic run also logged `WARNING: Multiple instances of Three.js being imported.` No separate visible failure was isolated to that warning. `net::ERR_ABORTED` during panel/context teardown is distinguished from an actual server HTTP 502.

Performance entries over one second are retained in each trace's `network` array. `openMs` measures the opener click through a visible dialog; `totalMs` includes screenshots, deliberate waits, keyboard probes, and every sub-option and must not be treated as UI latency. A shared, busy SwiftShader runner cannot establish production GPU frame-rate performance. The audit observed slow opens and actual HTTP outages separately; it did not run a paid generation or a load test.

Representative measured opens: Gazette at 1280: 16,884 ms; Members at 1280: 5,906 ms; Help at 1280: 3,900 ms; Compete at 1440: 3,679 ms; Mayor at 1440: 2,991 ms. The [aggregate evidence](QA-013/screenshots/summary.json) retains the other measurements. These are runner observations requiring confirmation on judge hardware, not independent P1 findings.

No focus trap was confirmed. An initial 250 ms dismissal probe was too short for three dialogs. The targeted [dismissal follow-up](QA-013/screenshots/dismissal.json) confirmed a single Escape closed Create village, Help, and Weekly review at both 1280 and 390 widths. Measured times were respectively 1,687 / 3,352 / 327 ms on desktop and 2,898 / 1,382 / 788 ms on mobile.
