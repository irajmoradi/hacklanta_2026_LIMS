### QA-010-00 — P1: intermittent API outage prevents Settings load and interrupts goal saving

**Observed sequence:** choose Stefanny → My goal → save the unchanged goal; later open Gazette, Village → Our group photo, then Settings at 390 × 844. During this live sequence the goal displayed “Failed to fetch” and Settings displayed “Request failed (500). Please try again” followed by “Loading your settings…” and Retry settings. The Settings screenshot was captured at **20:04:38 UTC**. These operations had worked earlier.

**Network/console evidence:** `deep-remaining.json` records nine HTTP 500 responses during Stefanny's pass: profile, village, `/api/me`, unread-count and five presence heartbeats. Responses took 5–23 ms and had empty or `Internal Server Error` bodies. The goal attempt emitted `net::ERR_CONNECTION_FAILED`. Screenshots: [failed goal save](QA-010/Stefanny-deep-goal-save-existing-failure.png), [Settings unavailable](QA-010/Stefanny-deep-responsive-failure.png).

**Reproduction status:** intermittent, not reliably reproduced by the UI sequence alone. Immediate later checks of both `:8010/api/me` and `:4173/api/me`, using the same seat, returned 200. The shared checkout changed during the run; a restart/redeployment is plausible, but was not established from server logs. Do not label this a deterministic Settings or database defect based on this report.

**Expected/impact:** the demo's core read/write routes remain available throughout normal navigation. A demo presentation would be blocked while this condition persists. The frontend preserved the goal draft and offered a Settings retry, which are useful recovery behaviors.

**Suspected area/files:** running API/proxy lifecycle; `apps/web/vite.config.ts` proxy, `apps/api/app/main.py`, `apps/api/app/db.py`. Correlate server/deployment logs around the timestamp before assigning an application fix. No server processes were restarted by QA-010.

### QA-010-01 — P2: core interactions exceed one second; refresh keeps successful saves busy

**Reproduce**

1. Open the live preview, choose Iraj, and open My profile.
2. Change Idle activity, or choose House → Modern → Save house.
3. Watch the disabled controls/loading state until the operation completes. Also open Shop from the town and wait for its inventory/balance.
4. In Network, filter the village root read and profile/feed reads performed after the mutation.

**Observed:** the first deeper run recorded 2.46–5.20 s for activity changes, 5.98 s for House save, 5.09 s for a daily check-in, and a shop village read of 11.54 s. A successful progress POST (HTTP 200, 4.47 s) was followed by more than five seconds with the check-in dialog still mounted. This was a timing assertion failure, not evidence that the check-in was lost. After returning to a single QA-010 browser, Iraj still took 2.53–2.73 s per activity change, 2.50 s for House save and 2.01 s to save an unchanged goal.

**Independent evidence:** six sequential plain Node village reads, without Playwright screenshots, returned HTTP 200 in 0.615–3.761 s; five exceeded one second. Direct API samples: 2296, 615, 1332 ms. Preview-proxy samples: 3761, 1971, 1073 ms. See [direct-timings.json](QA-010/direct-timings.json), [results.json](QA-010/results.json), [deep-results.json](QA-010/deep-results.json) and [preliminary-deep-results.json](QA-010/preliminary-deep-results.json). Screenshot: [check-in still mounted after response](QA-010/Iraj-deep-checkin-progress-failure.png). A later Stefanny goal retry returned 200 but its dialog remained mounted after a 20 s assertion window ([retry evidence](QA-010/goal-retry-results.json)); Mario's unchanged goal save completed in 28.43 s and House save in 19.59 s in the default-headless pass. These worst cases occurred on a busy shared host and must not be treated as isolated production latency measurements.

**Expected:** satisfy the task's ≤1 s interaction target, or promptly acknowledge accepted writes and refresh the village without holding the form busy. No evidence of a rendering-only explanation: API reads were also slow outside the browser.

**Suspected files:** `apps/web/src/App.tsx` (`refresh`, `submitCheckIn`), `apps/web/src/components/IdleActivityPicker.tsx`, `HouseEditor.tsx`, `Wardrobe.tsx`; `apps/api/app/main.py:get_village` and `apps/api/app/domain.py:villager`. Village assembly performs sequential per-member reads; several UI paths wait for full village/profile/feed refreshes. This is a profiling lead, not a measured database root cause.

### QA-010-02 — P2: demo-seat conflict warning overlaps mobile welcome text

**Reproduce**

1. Choose a seat in one fresh browser context.
2. Within ten minutes, choose the same seat in a second fresh context, so the real `/api/demo/seat` response reports a conflict.
3. Set the second viewport to 390 × 844 and close any open panel.

**Observed:** “Another tester chose Iraj in the last 10 minutes” flows below the white header and collides with “SMALL STEPS. GOOD COMPANY.” The main town and panels remain usable; this is a visible layout defect. No horizontal document overflow was needed to reproduce it.

**Evidence:** [Iraj mobile town](QA-010/Iraj-deep-mobile-town.png). `/api/demo/seat` succeeded; the collision is a DOM/CSS issue, with no required console error. The duplicate session is deliberate QA context, not an unexpected authentication failure.

**Expected:** reserve header/banner space for the conflict warning and position the welcome content below it.

**Suspected files:** `apps/web/src/components/DemoTools.tsx` (unclassed `role="status"` help-text sibling), `apps/web/src/styles.css` (mobile fixed-height header/grid and `display:contents` topbar-right rules).

### QA-010-03 — P2: enabled colosseum management buttons have dark text on dark backgrounds

**Reproduce**

1. Choose Stefanny, open Compete and select the existing `h` competition, whose auditor is Stefanny.
2. Open **Submit / manage competition**. Do not settle the competition.
3. Inspect the enabled **Settle competition** button. In the earlier list-based build, **All competitions** also showed the same problem.

**Observed:** management-panel buttons inherit the panel's dark navy text while retaining a dark button background. Labels are much harder to read than adjacent controls. This is not merely an intentionally dimmed disabled action.

**Evidence:** [Stefanny management controls](QA-010/Stefanny-deep-arena-controls.png). The final verifier confirmed the enabled Settle competition button still uses `rgb(41, 37, 56)` text on `rgb(67, 95, 55)` at 14 px, a calculated foreground/background contrast of **2.07:1**. See [computed styles](QA-010/verify-results.json). The newer layout's screenshot caught its panel transition, so the earlier settled screenshot is the clearer visual evidence. No failed network request or console exception is necessary to reproduce the color defect.

**Expected:** keep enabled action labels readable against their backgrounds when moving between the dark arena and light management panel.

**Suspected file:** `apps/web/src/components/colosseum.css`, especially `.arena-manage` and `dialog.modal.arena-modal .colosseum button { color: inherit }`, which overrides the normal primary-button foreground.

### QA-010-04 — P2: photo-token Buy stays enabled when the seat cannot afford it

**Reproduce**

1. Choose Mario with less than 25 XP (10 XP after the text-only QA daily check-in).
2. Open Shop → Make it real.
3. Click the enabled **Buy photo token · 25 XP** button.

**Observed:** the UI offers the purchase without a shortage/lock reason. `POST /api/villages/13370000-0000-4000-8000-000000000000/items/token` returns **409**, `{"detail":"Not enough XP"}` (757 ms in this attempt). The error appears only after clicking. Ordinary shop items correctly show shortage reasons and disable their Buy buttons in the same seat.

**Evidence:** [Mario token error](QA-010/Mario-deep-token.png), [deep-mario.json](QA-010/deep-mario.json), and the balance/button-state read in `verify-results.json`. The server's rejection is correct; the defect is the avoidable enabled purchase in the client. No token or external generation job was created for this failed purchase.

**Expected:** show the XP shortfall and disable Buy until affordable, consistently with the rest of the shop.

**Suspected file:** `apps/web/src/components/PhotoItems.tsx`: the shop fetch retains the token price but not the balance, and the button checks only `busy || price === null`.

### Test side effects and harness corrections

Clearly marked QA-010 text check-ins, unchanged-goal feed events, purchased cosmetics and photo tokens remain in the demo; the allowed test-XP purchases were not refunded. Reaction state and temporary idle/house settings were restored. No paid or external-send route was permitted by the runners.

**Cleanup caveat:** a preliminary seat-transition race caused the harness to read Iraj's identity before Lance's switch settled. The permission guard blocked the mismatched Settings request, and the harness now waits for the selected identity. Lance's temporary Modern house was reset to automatic style/palette (HTTP 200). His original custom override was not retained, so exact pre-test customization restoration cannot be proved; automatic was chosen to match baseline appearance. See [cleanup.json](QA-010/cleanup.json). No privacy-field change from that attempt reached the server.

Selector/encoding corrections and the house-field/competition-layout deployment required interrupted preliminary runs. Those interrupted runs and guard-generated `ERR_BLOCKED_BY_CLIENT` messages are **not** reported as product regressions. The actual 500 outage, connection failure, slow UI assertions and insufficient-XP response are distinguished above. One additional resource-404 console message during the outage lacked a retained URL and is not counted as a separate confirmed asset bug.
