### QA-011-00 ? P1: intermittent service unavailability still interrupts profile loading

**Observed reproduction:** select Maya in a fresh session at 1440?900, then open My profile during the live run. The profile displays ?Village is restarting, try again in a moment? and Retry profile instead of its tabs. The automated tab wait expires after 30 seconds. This is intermittent; the same seat later loads at 1280?720.

**Evidence:** [failed profile](QA-011/maya-profile-interruption-1440.png), final browser results below. The captured console contains repeated ?server responded with a status of 503? errors during Maya's town/profile stages, alongside aborted village/profile/competition reads. The original listener recorded statuses only after request completion; retry response-body cancellation explains why its status list alone does not enumerate these 503s. Future harness runs also capture response headers. Independent reads after the interruption all returned 200 in 36?316 ms. No prohibited write was involved.

**Second occurrence:** Stefanny's later focused profile at 1280?720 also displayed the restart state and a Reconnecting toast ([screenshot](QA-011/stefanny-profile-interruption-1280.png)). The improved response listener captured HTTP **502** on profile, village, feed, weekly, competition, avatar, heartbeat, unread-message, and demo-seat routes. This independently reproduces the availability symptom beyond Maya's earlier 503s; see `screenshots/details-rest.json`.

**Expected:** routine profile navigation remains available; planned deployment interruptions recover promptly. The visible retry state is useful, but does not resolve the availability failure.

**Suspected area:** deployment/proxy/API readiness and `apps/web/src/api/retry.ts` / profile loading in `App.tsx`. The client maps exhausted transient retries to this message. Server/proxy logs at the interruption time are required to determine the root cause; this report does not attribute a 503 to a specific application function. Carry forward QA-010-00 as **still observed**, now with HTTP 503 rather than 500.

### QA-011-01 — P2: locked shop cards expose internal reward-source identifiers

**Reproduce:** select Iraj, open Shop at 1280×720 (also visible at 1440×900), and inspect Auditor Badge and Champion Mantle in Village Shop. No purchase is needed.

**Actual:** the lock-reason bullets say `Earn-only: earned:auditor` and `Earn-only: earned:weekly_crown`. Readable earning descriptions appear immediately below, so the internal identifiers are both redundant and inconsistent with the plain-language copy pass. The problem affects the first cards a user sees on entering the shop.

**Expected:** a short readable reason such as “Earn by completing an audit” / “Earn the weekly crown,” or just the existing earning instructions.

**Evidence:** [1280×720 screenshot](QA-011/shop-internal-source-1280.png). The focused current-deployment screenshot shows both raw identifiers. The full-page capture is not used to judge thumbnail visibility. A separate [unredacted static-card crop](QA-011/catalog-card-static.png) confirms the Auditor Badge art renders and shows the same raw reward identifier. No HTTP error or console exception is required.

**Suspected files:** `apps/web/src/api/shopState.ts:24` adds `Earn-only: ${item.source}`; `apps/web/src/components/Wardrobe.tsx` renders the raw reasons alongside the readable `sourceLabel` / description. Reuse the source-to-label mapping rather than displaying the identifier.

### QA-011-02 ? P2: leaving a house interior returns focus to Close profile

**Suspected file:** `apps/web/src/components/ProfilePanel.tsx`: the effect depending on `[mobile, inside]` calls `close.current?.focus()` whenever `inside` becomes false, overriding return to the room opener.
